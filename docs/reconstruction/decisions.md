## ADR-001：计算引擎的重构边界

- 状态：Accepted（Q1 的重构范围）。
- 用户决定：彻底重构插件、模型转换、运行管理和结果解析，保留 `RCBldEng.exe` 计算内核。
- 不包含：恢复/接管引擎 Python 源码、重写 RC 算法或更换求解器。日后扩展需要另行决策。
- 事实：EXE 是 Windows x64/PyInstaller/CPython 3.12，归档未提供可编辑引擎 Python 源码；现有入口固定 `order=1`，不能据旧组件端口承诺二阶计算。
- 后果：`.sim/.sol/CSV` 和旧命令行约束必须由独立引擎适配层承接；保留引擎不等于保留旧组件结构、GUID 或错误行为。
- [推断] 本地端到端计算受 Windows x64 EXE 限制；Python 或 Rhino 支持 macOS 不会使该 EXE 自动跨平台。默认按 Windows x64 设计本地运行，不自行增加远程服务。
- 验收边界：同输入对照用于识别外围迁移偏差；旧引擎输出不是物理真值。引擎内缺陷须如实记录并限制功能承诺，不能在结果层静默修饰数值。
- 未决：可运行基准、物理/参考案例及数值容差；不影响已确认的重构范围。

## ADR-002：交付入口与技术栈约束

- 状态：Accepted（Q2 的入口、职责分离，以及用户补充的 Python/Rhino 8+ 方向）。
- 用户决定：仍以 Rhino/Grasshopper 插件为主，用户在 GH 中建模、配置和计算；把核心逻辑从 GH 组件中分离。
- 用户技术方向：基于 Python 重构，面向 Rhino 8 及以上。取代首轮“优先 C#”的候选建议，不要求为调用 EXE 新建 Python 服务。
- 分离原则：GH 组件负责端口、DataTree 映射、交互与结果展示；几何适配负责 RhinoCommon/Brep；领域、校验、引擎协议、运行管理与结果语义不得依赖 GH 组件生命周期。
- 独立核心不是独立几何内核：核心接受已转换的热区/边界/工况数据，不接受 `Rhino.Geometry.Brep`、`GH_Goo` 或 `DataTree`。几何前处理仍允许依赖 RhinoCommon。
- 非默认交付：与 GH 同等优先的 CLI、桌面独立程序、Web 服务、数据库、云计算；内部模块可在普通 Python 中调用，不因此承诺上述产品入口。
- 已确认旧 GH 定义采用干净切换，见 ADR-005。仍未决：最低 Rhino 8 小版本与后续大版本的验证矩阵、插件发布路径。不能把“面向 8+”写成已测试所有未来版本。
- 运行时及发布建议见 ADR-004；官方事实见 [Python/Rhino 核对](evidence.md#pythonrhino-8-技术约束核对)。

## ADR-003：结果的适用范围与正确性验收

- 状态：Accepted（Q3 的使用场景及指标方向）；指标定义和容差尚未批准。
- 用户决定：用于早期建筑设计比选，比较方案能耗、冷热负荷和趋势；用户在 Q6 补充主要面向办公建筑和住宅建筑，不代表要求将两种不同用途直接按总能耗排名。
- 产品边界：不宣称用于施工图设备选型、规范合规证明或经认证的科研计算；“比选”也不自动包含寻优算法。
- 指标建议：建筑年/月能耗及面积归一化指标；冷/热累计需求与峰值；逐时/月度变化及相对基准方案差异。能源边界、面积口径、正负号、时间步长、单位和峰值算法须逐量核实后确定。
- 关键区分：冷/热需求不等于 HVAC 输入能耗；累计能量不等于峰值功率。旧月报的统一求和再乘 `1e-6` 不能直接解释为所有列都是 kWh。
- Q7=A 已确认比较建筑设计变量时固定系统与使用工况。具体比较契约建议：天气、计算时段、时间轴、引擎及预设版本等非研究条件保持一致；人数/设备总量等随面积派生的量不强制相等，而应固定其密度和配置规则并展示实际总量。缺失列或失败方案不得按零能耗参与比较。
- 验收建议分两层：同一引擎、同一协议输入的迁移对照；控制变量案例与独立参考检验趋势和适用性。排序稳定性不能代替绝对量纲和计算正确性。
- 已知限制：归档无随包 EPW、`.sim/.sol` 或结果 CSV 基准；此前未实际运行引擎。尚不能证明数值精度或结果接口已端到端可用。

## ADR-004：Python 运行时与插件组织

- 状态：Proposed；下述为针对已确认方向的技术建议，不是新增用户承诺。
- 一手事实：McNeel 文档列 Rhino 8 内置 CPython 3.9.11；Script Editor 可把脚本发布为 `.gha`、共享代码库并生成 Yak 包；GH 不支持靠 `# async: true` 实现异步组件。来源与约束集中记录在 [现状证据](evidence.md#pythonrhino-8-技术约束核对)。
- 建议首选：Rhino 内置 CPython 执行轻量 GH 适配层和独立 Python 包；原 EXE 作为子进程执行计算。代码主要维护在可版本管理的 `.py` 文件，不把业务代码复制进每个 GH 脚本组件。
- 建议发布：先验证官方 Script Editor 项目发布路径，目标是可安装的 GH 插件，不把“交付一组散落脚本”当作插件交付。发布产生的 .NET 包装层不等于重新选择 C# 业务核心。
- 版本约束：若选择宿主内运行，核心必须兼容宿主 Python 3.9 的语法、标准库和依赖；现有 `pyproject.toml` 的 `>=3.13` 不能原样沿用。EXE 自带 Python 3.12，与宿主之间通过进程/文件通信，无须统一解释器版本。本轮不先修改空项目配置。
- 取舍：另起 Python 3.13 进程可解除宿主版本约束，但增加解释器部署、数据传输与进程生命周期成本；目前没有业务证据要求它，暂不引入。官方环境隔离说明也不保证同一 Rhino 进程内不同包版本的运行时隔离，应保持依赖精简。
- 建议职责划分：
  - GH 适配：端口、树结构、命令触发、诊断呈现、回写结果。
  - Rhino 几何适配：几何量、单位换算、朝向、相邻关系、几何诊断及模型转换；不放进组件主体。
  - 领域/应用核心：热区、边界、材料、工况、日程、方案及可解释的模型校验；不引用 Rhino/GH。
  - 引擎适配与运行：生成旧协议、准备文件、启动/终止子进程、捕获退出码和日志、确认本次产物。
  - 结果/比选：按表头识别量、核实单位与时间轴、聚合指标并关联方案；不按旧 CSV 固定列号解读。
  - 国际化呈现：英文主界面及独立翻译资源；诊断、组件说明和结果标签在呈现边界本地化，不把翻译逻辑放进热工计算或引擎协议。
- 运行约束建议：明确的运行触发，不在每次 GH 求解时重复启动或删除旧结果；运行使用输入快照与独立标识，参数改变后旧结果不可冒充当前结果。后台进程等待不得阻塞 GH 求解；完成后通过宿主允许的调度更新输出。
- 文件约束：EXE 从子进程 `cwd` 的父目录找 `Projects/<project>/<run_id>`；独立运行目录必须符合此布局，不是任意设置一个临时目录即可。不得修改 Rhino 全局工作目录；不得让不同运行互相覆盖产物。
- 实现前验证门槛：在目标 Windows/Rhino 8 上验证 Python 包导入、`.gha` 安装、GH 多次求解/文档关闭时的任务生命周期，再用真实天气和模型打通 EXE→结果。当前只有静态与官方文档证据，没有宿主运行验证。

## ADR-005：旧 GH 定义干净切换

- 状态：Accepted（Q4=A）。
- 用户决定：不要求旧 `.gh` 无修改打开并运行；可重新设计组件和端口，提供新工作流的对应示例。
- 后果：不以旧 GUID、端口顺序或持久化类型约束新架构；不默认提供兼容组件、别名或自动迁移工具。
- 保留边界：归档 `example.gh` 和源码仍是行为/业务调查材料，不因干净切换而删除。取消文件兼容不等于取消旧功能；功能覆盖在完整方案中逐项确认。

## ADR-006：已划分热区的闭合 Brep 入口

- 状态：Accepted（Q5=A 的主要建模工作流）。
- 用户决定：用户提供已经划分热区的闭合 Brep，系统识别围护边界与相邻关系，并允许人工修正。
- 责任边界：热区划分由用户决定；本次不因建模入口选择而新增“总体量自动分层/分热区”算法。热区不强制等于单个真实房间，也不能默认整栋建筑就是一个热区。
- 建议数据约定：主入口按一个闭合 Brep 对应一个热区处理，材料、使用工况和日程关联到热区；此具体映射仍需在模型契约中确认，不把用户的入口选择扩写成所有几何限制均已批准。
- 建议模型校验：非闭合/退化几何、重叠空间、局部接触和边界歧义应提供可定位诊断；人工修正也要满足邻接一致性。不得把不能识别的内边界静默当作外墙。
- Q8=C 已确认窗与遮阳采用参数化和显式几何两条路径，具体覆盖规则见 ADR-009。Q10=B 已确认空调区与非空调区共同建模，Q11=A 已确认平面围护（含非正交平面和坡屋顶）、曲面由用户先简化，见 ADR-012～013；这些需求不等于现有引擎效果已经验证。

## ADR-007：办公/住宅的顺序批量比选

- 状态：Accepted（Q6=B 及建筑类型）；规模、性能目标和指标细则未定。
- 用户决定：GH 一次提交一组方案，自动依次计算并汇总。用户尚不确定方案数量；主要面向办公和住宅建筑。每方案热区数也未提供，不反复要求用户先猜规模。
- 执行边界：默认同一批次一次计算一个方案，不将批量解释为并行启动多个 EXE；不默认新增优化器、分布式调度或外部数据库。
- 数量边界：按实际提交的方案集合运行，不写死方案数或把示例数量当作上限；规模能力须以真实模型和目标机器实测确定，不能宣称不限量或保证吞吐量。
- 语义建议：方案表示待比较的建筑模型与配置；运行表示某方案的一次计算；批次表示一组方案的执行与汇总。三者标识分开，同一方案再次运行不覆盖既有计算证据。
- 汇总建议：结果保留方案关联与成功/失败状态，成功结果可比较，失败项单独显示诊断，不能按零能耗填充。批次显示已完成数量/总数量；不伪造内核计算百分比。
- 工况建议：办公/住宅用途通过可编辑的热区工况及日程表达，而非仅在建筑上设置两个全局标签。Q9=B 已确认有来源、可覆盖的中国优先预设，并需满足国际化，见 ADR-010～011。Q10=B 已明确纳入非空调区，见 ADR-012；不因此推定任意混合用途组合均已验证。
- 比较建议：同用途、同服务条件下比较设计改动；跨用途比较时显式展示面积、人员、日程、设定温度和统计边界，不能直接把能耗差异解释为设计优劣。
- 未决：批次中失败后的继续/停止策略、取消边界和性能目标。在完整方案中提出保守默认值，不因本轮未问而声称已获用户批准。

## ADR-008：固定工况的建筑设计比选

- 状态：Accepted（Q7=A 的主要比较模式）；具体一致性检查规则为建议。
- 用户决定：主要比较体形、朝向、围护构造、窗墙比和遮阳等建筑设计变量，系统与使用工况保持一致。
- 保留输出：能耗、冷热负荷和变化趋势；不是只计算负荷，也不是完全去掉系统效率输入。
- 不新增：系统选型寻优或运行控制策略优化；已有 HVAC 等输入仍用于确定共同的计算条件，不因不作为研究变量而删除。
- 建议批次契约：共享天气、日程、温度设定、人员/设备密度及系统配置规则；各方案保留自身几何、构造和显式研究变量。面积改变导致的人员/设备总量变化须可解释，不把“固定工况”误作固定所有派生总量。
- 建议结果呈现：总量与明确面积口径的强度指标并列，记录共同条件和方案差异；服务面积或服务条件变化时不只靠总能耗排序。

## ADR-009：窗与遮阳的双路径输入

- 状态：Accepted（Q8=C 的两种输入能力）；下述覆盖规则及算法细则为 Proposed。
- 用户决定：参数化输入与显式几何输入都需要；默认参数化，必要时使用实际窗面、遮阳构件及周边建筑几何。
- 参数化路径：按朝向/围护面设置窗墙比与简化遮阳参数。其简化假设必须可见，不能等同于真实遮挡几何。
- 显式路径：窗面需与所属围护关联，遮阳和周边建筑进入太阳/遮挡前处理；遮挡物不是自动生成的热区。
- 建议窗输入优先级：以同一围护面为边界，显式窗输入覆盖该面的窗墙比生成结果；没有显式覆盖的面继续用参数化设置。明确区分“未提供显式窗”和“显式指定无窗”，避免 WWR 意外补窗。最终几何和面积需可预览。
- 建议遮阳规则：简化遮阳与显式遮挡各有清晰的作用范围；同一遮挡作用不允许两次折减。不同构件确需组合时必须有明示的计算规则，不能只因两种输入都连接就叠乘系数。
- 引擎边界：旧 `.sol` 接收热区窗/不透明部分的太阳序列，不是通用遮阳几何接口；必须核实单位、归一化面积、时间轴及内核如何组合太阳项。两条路径都在需求内，协议约束不能被用作悄悄取消显式路径的理由。
- 验收建议：无额外遮挡且使用相同窗几何/太阳假设时核对两条路径；有遮挡时分别验证入射/得热及最终负荷，不能仅以年总能耗降低作为“遮阳正确”的证据。

## ADR-010：中国优先的可追溯工况预设

- 状态：Accepted（Q9=B、中国为主要应用地区）；具体数据来源、标准版本和数值尚未批准。
- 用户决定：提供有明确来源与适用地区的办公/住宅预设，并允许逐热区覆盖；主要用于中国。
- 必须区分：用户已选“中国优先”不等于已指定某一 GB/JGJ 标准，更不等于已认可旧代码默认值。不得补造人员密度、照明功率、温度设定或日程数据。
- 建议资料组织：预设按地区、建筑/空间用途及适用条件组织；界面语言不参与选择工况。中国内不同气候区、运行场景不能仅用一个无条件的“中国住宅”模板混同。
- 建议来源记录：来源名称、发布机构、版本/年份、条款/表号或数据定位、适用范围、参数单位，以及必要的使用/再分发许可；同一模板引用不同资料时按参数追溯。
- 参数语义：规范限值、计算参考工况、统计典型值与用户自定义值分开标识；不能把规范上限直接标成实际运行值。
- 建议覆盖与复现：载入特定版本预设后生成明确参数，用户修改保留来源与覆盖记录；运行保存最终参数及预设版本。更新预设库不追溯改变旧模型或历史结果。
- 资料缺口：本轮只确认来源要求，没有完成中国标准资料调查，也未填入任何预设数值。权威来源与可合法分发的数据需在预设实现前核实；不能用占位值交付“有依据预设”。

## ADR-011：国际化边界

- 状态：Accepted（用户明确要求国际化，并补充界面先以英文为主、通过 i18n 实现多语言支持）；额外语言的交付清单、地区资料覆盖及下述具体实现规则仍为 Proposed。
- 用户决定：English-first；英文作为主界面与基准文本，从开始就采用 i18n 实现多语言支持，而不是先把英文写死在组件中、以后再整体改造。
- 文本资源建议：组件/端口名称与说明、菜单、校验诊断、运行状态、指标标签及导出报告的展示文本均通过独立资源查找；首批附带简体中文翻译作为建议，不能写成用户已批准的语言清单。不自动翻译用户命名或引擎原始日志。
- 回退与诊断建议：缺少某语言译文时回退到英文；英文基准资源缺失应在发布检查中暴露，不能把资源键当作正常界面文本。诊断保存稳定代码、对象定位和参数，再按界面语言呈现；历史错误不依赖某一语言的整句文本识别。
- 语言与地区分开：界面语言、工况资料地区、天气地点和单位显示各自设置；英文界面可使用中国预设，中文界面也可查看其他地区模型。切换语言不得暗中切换天气、工况或计算规则。
- 标识与显示分开：模型/组件/指标使用稳定的非本地化标识，名称和说明独立翻译；用户可使用中文或其他语言命名。不得用翻译后的文本作为内部引用键，也不翻译原引擎协议关键字。
- 数值与单位建议：核心按各物理量的统一单位处理，Rhino 几何输入、界面显示及引擎协议分别转换；不把中文界面等同于“输入一定是米”。机器数据的小数、日期格式固定，显示本地化不改变解析。
- 天气/日历建议：显式携带天气位置、时间基准、日历及日程含义，不写死东八区、北半球、当地夏令时或中国节假日。不随系统区域设置自动变更计算时间；若引擎不支持某时间规则，应明确诊断或采用经确认的转换，而非静默错位。
- 预设扩展建议：地区资料与领域模型分开，通过同一数据契约添加经核实的地区配置；不为“中国/美国/欧洲”分别实现热区或运行逻辑。国际化不等于本次已承诺附带所有地区资料、国际规范认证或任意气候场景的数值适用性。
- EXE 约束保持：国际化不解除 Windows 本地计算限制；中文/非 ASCII 用户名称、目录与不同区域设置须在真实 Windows/Rhino/EXE 上验收。协议内名称映射由适配器负责，不先假定 EXE 接受任意用户字符串。
- 建议不变量：仅切换界面语言或显示单位时，规范化物理模型及模拟结果应相同；修改地区预设才是物理输入变化，必须显式体现为模型变化。

## ADR-012：空调区与非空调区共同建模

- 状态：Accepted（Q10=B 的需求）；引擎映射及数值能力待验证。
- 用户决定：需要楼梯间、走廊、不供暖空间等非空调区与空调区共同进入热模型；非空调区不主动维持供暖/制冷设定温度，其自由室温及与相邻区的传热仍参与计算。
- 建模建议：把热区是否主动供暖/制冷与使用工况、是否有人、内部得热、通风渗透分开表达。非空调不等于无人、无得热、室外、绝热或从模型中删除；也不能仅靠没有连接 HVAC 输入推定非空调状态。
- 输出建议：保留非空调区室温及其对相邻区负荷的影响；建筑总面积与受调节面积分开记录，强度指标明确分母，不能把新增非空调面积造成的数值下降解释为节能。
- 能力验证：核对旧协议、温控分支、热区耦合与室温输出，再用“受调节房间 + 非空调缓冲空间”的控制变量案例确认自由室温和相邻传热。暂不认定关闭 HVAC 日程就足以表达完整需求。
- 不包含：自然通风气流网络、新通风算法或舒适度认证；已有通风/渗透输入不因此取消。
- 不允许的替代：极端设定温度、静默绝热、把邻区温度替换为室外温度均不能冒充非空调区支持。若保留的 EXE 无法表达需求，必须提交能力差距请用户决定，不自行缩减需求或改写引擎。

## ADR-013：平面围护及用户负责的曲面简化

- 状态：Accepted（Q11=A 的主要几何范围）；容差与引擎映射规则仍为 Proposed。
- 用户决定：热区围护以平面为主，包括非正交平面和坡屋顶；曲面由用户在输入前简化。本次不承诺直接接收曲面并自动完成受控离散化。
- 与 Q5 的关系：主入口仍是用户已分热区的闭合 Brep；Brep 的数据类型本身不证明各围护面满足平面要求。应按明确容差检查平面性、闭合性和有效体积，并定位未满足要求的面；不能只采样一个法线就通过曲面。
- 几何建议：保留真实面积、法线、项目北向及边界邻接。倾斜面分类与热边界语义分开，不直接沿用旧法线阈值或把坡屋顶当成水平屋顶。容差由模型单位和宿主几何容差形成明确规则，具体数值不在访谈中任意指定。
- 引擎约束：旧实现存在八方向聚合，尚未证明协议能精确表达任意朝向/倾角。必须逐项核实非正交平面、坡面传热及太阳输入的表示；有近似时说明作用范围并提交复核，不静默投影或吸附朝向。
- 窗与遮阳：Q8 的参数化/显式双路径保持。Q11 确定的是热区围护入口，不取消显式窗、遮阳构件或周边建筑，也不自动承诺任意曲面遮挡物的处理能力；遮挡几何接受规则在太阳前处理契约中明确。
- 验收建议：正交盒体、旋转盒体、含非正交墙面的闭合体及坡屋顶案例；检查单位换算、面积、朝向、部分接触与邻接一致性。未简化曲面应给出可定位诊断，而不是生成看似有效的热模型。

## 完整方案复核（Proposed，待用户整体确认）

本节把已确认需求落到同一条交付链上；不是新增问卷，也不是实现已完成的声明。上面标为 Accepted 的需求保持，以下技术默认值需整体复核。

### 交付链与模块边界

```text
GH：分区闭合 Brep + 材料/工况/日程 + 天气 + 窗/遮阳 + 方案集合
  → Rhino 几何适配：平面校验、单位/北向、边界/邻接、窗与遮挡前处理
  → 独立 Python 核心：热区/边界/工况、模型校验、共同条件及方案差异
  → 运行快照：方案标识、最终输入、天气与预设版本、独立运行目录
  → 引擎适配：.sim/.sol → 原 RCBldEng.exe（同批次顺序执行）
  → 结果解析与比选：时间轴/单位/能源边界 → 指标、趋势、状态及诊断
  → GH 呈现：English-first + i18n；语言切换不改变物理输入
```

- 采用 ADR-004 的宿主内 Python 核心与薄 GH 适配，优先验证官方 Script Editor → `.gha`/Yak 发布路径；最低 Rhino 8 小版本由实际导入、发布及生命周期验证确定，不把未知最低版本写成已支持。
- 核心数据建议以稳定标识连接热区、边界、材料、工况和日程；相邻边界关联双方热区及一致接触面积。领域数据不包含 Rhino/GH 对象，也不包含翻译后的内部引用键。具体字段与持久化 schema 在实现前的契约阶段定稿。
- 不新增独立 Web/桌面界面、服务、数据库或优化器；i18n 覆盖 GH 插件实际呈现面，不因此引入 Web 前端框架。

### 功能覆盖建议

| 能力组 | 新工作流承接方式 | 明确边界 |
|---|---|---|
| 材料与围护 | 材料/构造热工参数、平面围护识别、内外/接地/架空边界及人工修正 | 不把 U 值输入擅自升级为未验证的分层构造求解器；不静默猜边界 |
| 热区与工况 | 已分区 Brep、办公/住宅有据预设、逐区覆盖、日程、空调/非空调耦合 | 不提供自动分热区或新气流网络；非空调能力必须真实打通 |
| 窗、太阳与遮挡 | 默认参数化，支持显式窗/遮阳/周边建筑；预览有效几何和作用范围 | 同一面不重复计窗、同一遮挡不重复折减；核实 `.sol` 物理语义 |
| 基础与能源系统 | 天气、项目北向、地温、HVAC/COP、照明、DHW、泵、管理等级、能源来源与 PV/SWH/风机发电配置 | 承接有证据的旧输入能力并逐项核实引擎效果；系统为共同条件，不新增系统寻优 |
| 运行与比选 | 成组提交、顺序执行、取消、状态/日志、保留历史、汇总成功与失败方案 | 不写死方案数；不把 EXE 退出或文件存在直接视为结果有效 |
| 结果与交互 | 建筑能耗、冷热需求/峰值、趋势、热区室温、面积口径；必要的预览/烘焙及方案数据保存 | 不复刻重复/实验组件；额外舒适度输出先核实语义，不能承诺认证 |
| 安装与示例 | 可安装插件、新工作流示例、英文主文本及翻译资源、可追溯预设 | 不要求旧 `.gh` 原样兼容；归档保留作证据，不作为可运行新示例交付 |

旧目录或组件上出现的校准、敏感性、优化与二阶选项不构成已可运行功能；现有入口能力限制见证据。不用“干净切换”取消上表真实输入能力，也不逐文件照搬旧实现。

### 运行与结果的保守默认值

- 显式触发才启动批次，提交时冻结全部方案及共同条件；后续 GH 求解不重复启动。编辑模型后保留旧结果，但标明它属于旧快照，不能冒充当前计算。
- 建议单方案失败后保留诊断并继续其余方案，批次最终区分全部成功、部分失败和取消；共同输入无效则在运行前拒绝整批。基础设施故障导致无法继续时停止并说明原因，不自动重试或填零。
- 建议取消时停止后续排队并终止当前运行的进程树；已成功结果保留，未完成产物不作为成功结果。GH 文档关闭时清理本文件拥有的任务，后台完成回调不得访问已关闭文档；完成与取消竞争须有确定的终态。
- 指标按已核实的字段语义处理，累计能量与功率峰值分开；建筑峰值从同步建筑时序求取，不能将各热区不同时刻峰值相加。先检查时间轴、单位、能源来源及缺测，再计算月/年聚合与差异，不继承旧固定列号或无差别求和。
- 比选同时展示研究变量、共同条件、面积与服务边界。失败、缺列或不可比方案有明确状态，不默认参加排名；语言和显示单位变化不触发新的物理模型。

### 实施顺序与可观察验收门槛

1. **宿主与引擎能力验证**：在 Windows/Rhino 8 验证包导入、插件安装、后台调度和文档关闭；补齐有权使用的天气及真实 `.sim/.sol/CSV` 案例。优先验证非空调耦合、非正交/坡面表达、太阳输入和结果量纲。任何与保留引擎冲突的需求先报告，不靠后端兜底伪造支持。
2. **契约与依据定稿**：确定内部单位、北向/倾角、边界和容差、日程/日历/天气时间轴、指标能源边界、受调节面积、模型与运行标识、协议及结果 schema；核实预设来源、版本和分发许可。英文基准术语及资源键在组件落地前统一，地区资料独立于语言。
3. **端到端主链**：实现几何转换、工况与日程、双路径窗/遮阳、协议/进程管理和结果解析，经 GH 实际输入得到可定位诊断及真实结果；同时保留单方案路径，不用批量功能掩盖基本计算链缺陷。
4. **批量、国际化与交付**：打通共同条件校验、顺序批次、取消/历史结果、汇总比选及资源化界面；验证英语和所确认译本的实际呈现、非 ASCII 命名/目录、跨区域数值格式及语言切换前后的输入不变性。交付可安装包、新示例和运行说明，不交付空翻译壳或占位预设。
5. **正确性与发布验收**：相同协议输入的迁移对照，加上单位变换、平移/旋转、邻接、非空调缓冲区、太阳遮挡及日历边界案例，并用独立参考核对物理趋势与量纲。容差由真实基准确定，不凭空承诺精度；方案数和热区规模按真实机器记录性能，不设置任意上限。

现有验证缺口：尚无 Windows/Rhino/GH 运行证据、可运行天气/结果基准、已批准预设资料与数值、最低宿主版本及性能数据。静态证据不替代这些验收。下一步是用户复核本完整方案；确认后才启动实施，先执行能力验证门槛，而不是直接铺开组件。
